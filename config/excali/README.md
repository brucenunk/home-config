# Excalidraw palettes

Palettes are generated by home-config's `theme-builder` skill from the installed
Doric package. Home Manager's Emacs feature installs this directory at
`~/.config/excali/` (or `$XDG_CONFIG_HOME/excali/`). Read
`palettes/<theme>.json` before creating or deliberately restyling a diagram.
All 28 Doric 1.4.0 themes have a palette; the JSON is data, not executable code.

## Editor use

In excali-mode's native styling transient, choose **p — Palette: …**, then:

| Preset | Intended use | Doric source |
| --- | --- | --- |
| Default | Arrows, text and unfilled shapes | `default` foreground; transparent fill |
| Neutral | Ordinary filled boxes, such as service participants | `highlight` background, inherited `default` foreground |
| Accented | Highlighted boxes, such as a human participant | Paired `region` background/foreground |
| Muted | Secondary boundaries and lifelines | `shadow` foreground; transparent fill |
| Red, Green, Yellow, Blue, Magenta, Cyan | Meaningful diagram-specific categories or emphasis | Doric's corresponding `fg-COLOUR` / `bg-COLOUR` pair |

The six named colours are additional presets in the same palette menu (keys
`r`, `g`, `y`, `b`, `M`, `c`). They use each theme's own colours, not fixed hex
values. Their names do not assign semantics: Green does not automatically mean
success, for example. Choose and label meanings appropriate to the diagram.

Each preset contains `stroke`, `fill`, and `text` colours. Applying a preset
changes selected elements and their bound labels, and sets native defaults for
new ordinary shapes, lines, arrows and text. With no selection, only defaults
change. It sets solid fill but preserves geometry, line patterns, fonts,
opacity, and unrelated metadata.
Sticky notes and their labels are excluded from palette presets, including
when selected together with ordinary elements. Use the native colour pickers
for them. Note creation and label entry stay native, without our text-contrast
correction; native current-item defaults can still influence note text as usual.
Presets always set the defaults for ordinary drawing elements, even when the
selection contains only excluded notes.
Existing standalone text changes only when selected. Text uses the preset's
foreground when readable against its actual background; otherwise black or
white is used for contrast. Transparent containers and arrow labels use the
canvas, not the preset's box fill. Explicit native colour/fill overrides end
the active creation preset and continue to work normally.

The native colour pickers are unchanged. `M-x my/excali-use-preset` provides the
same preset actions outside the transient. Every explicit preset application
reads the **current Emacs theme's** palette; individual presets have no separate
Doric-theme chooser.
To style an existing element, select it, open the styling transient with
`M-x excali-style`, press `p`, then choose a preset. Its bound label is included;
unselected elements and the canvas remain unchanged.

The main menu recognises only the explicitly selected elements' actual palette
styling; it does not add a box's unselected label to the selection. A Neutral
box can therefore show Neutral even if its label has different ink. Selecting
both the box and that label shows Mixed. Applying a preset still styles the
box and its bound label together, as described above.
With no selection, the menu recognises the native
current-item defaults instead. It shows **Palette: Neutral**, for example,
**Mixed** for differing styles, or **Custom** when the styling matches no preset.
This works after saving/reopening because it compares colour/fill properties,
not the last preset command or stored roles. Where the properties cannot
distinguish multiple presets (such as standalone text with shared ink), it
uses a bound label's container to disambiguate where possible, then prefers
the first matching preset in the table above. A label can still match a
different preset from its parent. Equivalent native hex colours are normalised
before comparing styles. A common matching preset
across the selection takes priority over differences between shape and label
properties that do not apply to both.

Recognition is read-only, uses the current Emacs theme's palette, and never
changes colours, defaults, undo/redo or metadata. When automatic following is
skipped, old colours may show Custom until deliberately restyled.

An applied creation preset keeps its own colour snapshot until another preset,
native override or palette conversion is applied. Automatic theme following
converts recognised creation defaults and their active preset snapshot too.
Recognition alone does not activate this creation behaviour. The active creation preset is
buffer-local, not saved role metadata: native current-item defaults persist,
but after reopening, reapply a preset to enable its contrast-aware text creation.
To change just the canvas, use `my/excali-set-canvas-background`; its interactive
default is the current Emacs theme's background.

New drawings start with the active theme's palette canvas and Default style.
If that theme has no installed palette, they retain the original one-time
initialization from the theme's default background/foreground, without saved
palette metadata.

## Automatic theme following

Opening a native/PNG/SVG scene with usable palette metadata converts its
recognised palette styling to the current Emacs theme's installed palette.
Enabling a theme (including auto-dark changes and theme previews) does the same
for every open excali drawing, including hidden buffers. Already matching palette
snapshots are a no-op. Scenes without a usable saved palette and themes without an
installed palette are left alone; a bad scene does not block other drawings.
Drawings with pending redo are also skipped so an automatic edit cannot discard
that history. Redo the work, or deliberately start a new edit branch, before the
next open/theme event. There is no queued retry.

Automatic following uses the same conservative conversion described below:
custom colours, ambiguous styling, sticky notes and unrelated metadata are
preserved. Each conversion is one undo step, including canvas, defaults and the
saved palette. **Nothing is saved automatically**; save normally to persist
changes. Theme previews can leave modified buffers and conversion history even
if you return to the original theme.

Avoid switching themes while manually editing text or completing another native
multi-step edit. Text entry previews mutate live elements; a conversion can
capture unconfirmed text in undo history. There is no active-edit guard.

Saved palette metadata does not override the current theme for later explicit
preset applications. If the current theme has no installed palette, explicit
preset application reports an error without changing the drawing.

## Explicit diagram conversion

Run **`M-x my/excali-update-palette`** in a diagram buffer, then choose an installed
Doric palette to update that entire diagram. Completion requests alphabetical
order, with the current Emacs theme as the default when its palette is installed;
press `RET` to accept it. Vertico pins the default above the otherwise alphabetical
list. Input starts empty so you can browse or filter all palettes. If the current
theme has no installed palette, choose one explicitly.
The picker uses the same `theme` completion category as `consult-theme`, so
Marginalia shows its standard theme descriptions. With the configured Orderless
completion, type `&dark` or `&light` to filter by those annotations rather than
the palette names.

The highlighted palette previews **automatically as you move through or filter
candidates**, like `consult-theme`; no preview key is needed. Each preview starts
from the original scene, not the previous preview. Frame and minibuffer resizing
keep showing the selected preview. Press **`C-g`** to cancel: the original colours,
canvas, drawing defaults, active creation preset, metadata, modified flag,
selection and undo/redo history
are restored. Press **`RET`** to accept the selected palette: one normal conversion
is applied to the original scene.
Preview edits do not enter native history. The accepted conversion forms one
complete undo step. This does not preview or enable any Emacs theme.
Preview is render-only: editing, saving and history commands never operate on a
disposable preview scene. Large drawings may take longer to convert and redraw
when the highlighted candidate changes.
The explicit picker never changes the Emacs theme or other diagram buffers, and
has no transient entry. The selection does not restrict conversion. Save normally
when satisfied. Automatic theme following is separate from this picker.

Lisp callers can pass a palette name, e.g.
`(my/excali-update-palette "doric-obsidian")`; a call without an argument continues
to use the current Emacs theme's palette without prompting.

The command recognises presets using the single saved `palette`
snapshot. It converts matching shapes,
arrows, standalone text and bound labels, resolving label contrast against the
converted parent and canvas. Matching canvas colour and drawing defaults are
converted too; an already active creation preset receives the converted colour
snapshot. Conversion does not activate a creation preset after reopening.

Solid borderless rectangles whose fill matches the source palette's canvas
also follow a matching canvas conversion. This supports separate label
backplates: their transparent stroke stays transparent and only their fill
changes. It applies to all rectangles with that styling, not just those near
text; without roles an intentional same-colour rectangle is indistinguishable.
Patterned, custom-filled or non-rectangular shapes are not backplates. If the
canvas is custom and preserved, backplates are preserved too.

The six named presets are optional in saved palette snapshots; generated
palettes include all ten presets.
Applying a named preset missing from a saved snapshot extends `palette`
with that preset only when its theme, canvas and every existing preset value
match the installed palette. This lets diagrams use new colours and convert
them later, including after reopening.
Incompatible or missing palette metadata is not repaired by applying a preset; those
colours remain custom/unmatched unless the saved source already recognises them.
When a target lacks a needed named preset, affected elements and drawing
defaults stay unchanged rather than receiving guessed or invalid colours.

Custom/unmatched styling, sticky notes and their labels, deleted elements,
geometry, fill patterns, fonts, opacity and unrelated metadata remain unchanged.
A custom canvas or custom drawing defaults are preserved. Without per-element
roles, identical source styling can imply several presets: parent context helps
disambiguate labels, but if matching roles would produce different target colours,
the element is left unchanged. The command reports updated elements and ambiguous
or unsupported matches. Unmatched elements are not counted in that report.

Missing/invalid palette metadata or an unavailable/invalid target palette stops
conversion without edits. Native browser exports that lost palette metadata therefore
cannot be converted by this command. Use individual preset commands instead.

There is no separate initial palette or immutable provenance record. A successful
conversion replaces `palette` with the complete target palette snapshot,
preserving unrelated metadata. This becomes the source for the next conversion, including after
save/reopen; unmatched or ambiguous elements are not assigned persistent roles.
As with menu recognition, manually chosen colours indistinguishable from a preset
are recognised as that preset.

**Undo:** converted elements, canvas, drawing defaults, the active creation preset
and the saved palette form one native undo step, even when no elements change.
Undo/redo restore them together, so undo followed by a geometry edit and another
conversion uses the correct source palette. Views and unrelated document fields
are not restored. Local advice extends the native snapshot, comparison and restore
functions; no upstream package patch or second history stack is installed.

## Doric Light PNG export

Run **`M-x my/excali-export`** to export a PNG using the `doric-light` palette,
for example for Canva Docs. Choose the output filename as with native export.
There is no new keybinding; `C-c C-e` remains the native image-export command.

The command converts a disposable copy with the same conservative palette rules
as normal conversion: custom/unmatched styling is preserved. It never changes
the Emacs theme, source diagram, selection, modified flag, native caches or
undo/redo history, including if conversion/export fails or is cancelled. No undo
is needed afterward. The diagram must have a usable saved `palette`, and the
Doric Light palette must be installed.

With a selection, export just that selection (including native bound-label/frame
handling); use a prefix argument, `C-u M-x my/excali-export`, for the whole diagram.
Native scale, padding, background and embedded-scene settings are retained.
Custom canvas colours remain custom; disabling the background still produces a
transparent export. If scene embedding is enabled, the PNG contains the converted
Doric Light scene, not the original source palette.

## Org authoring and inline previews

The local `my-emacs-org-excali` module owns Org links, preview caching/layout,
and publication export. It requires `my-emacs-excali` for palette policy and
disposable native scene rendering; the drawing module does not load Org
integration. `config/emacs/init.el` loads both explicitly. Existing commands,
options and link syntax are unchanged; this is not a standalone package API.

Insert an authoritative scene with **`C-c C-l`**, choose **`excali`**, and
complete a `.excalidraw` filename. Completion starts in `my/excali-directory`
(`~/work/docs/diagrams/` by default), permits other locations, and stores a
path relative to the saved Org document. For a document in `~/work/docs/docs/`:

```org
[[excali:../diagrams/shared-image-build.excalidraw]]
```

Save the Org document first. Follow the link with `C-c C-o` to open the scene
in the existing editor. Both undescribed and described links preview immediately
after `C-c C-l` insertion/editing and when opening a document. For example:

```org
#+CAPTION: Image build sequence
[[excali:../diagrams/shared-image-build.excalidraw][Image build]]
```

The description supplies publication alternative text; `#+CAPTION:` supplies a
visible figure caption in HTML (an image title in Markdown). These rules apply
only to `excali` links, not ordinary described file links.
Org's `C-c C-x C-v` toggles previews, and
`M-x org-link-preview-refresh` explicitly redisplays/regenerates them.
Toggle a preview off to see and edit its source link with `C-c C-l`; following
the link still opens the authoritative scene. Layout changes do not turn hidden
previews back on.
Saving a scene (including native `excali-save`) refreshes displayed references;
enabling a theme refreshes displayed diagrams only. Ordinary prose edits do
not regenerate unrelated diagrams. External file edits are picked up on the
next explicit refresh or reopen; there is no file watcher.

Previews render **saved source**, not an unsaved editor buffer. A scene need not
be open in the editor. The native renderer converts a disposable copy to the
current theme using the conservative palette rules above. Source files, live
scene state, selection, native caches and undo/redo are untouched. Existing
automatic theme following for editor buffers is separate and remains unchanged.
Native SVG images—not Excalidraw JSON—are displayed inline. They scale without
enlarging a low-resolution raster. The native Cairo SVG exporter outlines fonts:
labels retain their rendered shapes without requiring the reader's fonts, but
label text is not searchable/selectable as text in the exported SVG.

Previews default to **100% of the window's text area**, excluding fringes,
line numbers and margins, including Writeroom's prose margins. Window resizing,
split views and Writeroom entry/exit resize already displayed previews without
rendering scenes again. This does not change global or buffer-local Org image
settings for other images. Override an individual diagram with:

```org
#+ATTR_ORG: :width 90%
[[excali:../diagrams/shared-image-build.excalidraw][Image build]]
```

An integer width (for example `:width 600`) specifies pixels. Widths are capped
at the available text area. Narrower standalone previews are centred by default;
`:align left` or `:align right` overrides that. Diagrams embedded in surrounding
prose are not given centring space. `ATTR_ORG` controls
editor display only; use backend attributes such as `ATTR_HTML` for publication.

Generated images are content-addressed by source content, target palette and
renderer identity under `$XDG_CACHE_HOME/excali/` (default `~/.cache/excali/`).
Theme changes never write generated images beside the source. Old cache entries
can be deleted at any time; they regenerate when needed. The first render of a
scene/palette is synchronous and may take longer for a large drawing.

### Publication export

Standard **HTML** (`C-c C-e h o` or `h h`) and **Markdown** (`C-c C-e m m`)
export renders the same
links in **Doric Light**, independently of the editor theme. Described links
also embed diagrams. The export parse tree uses generated SVG file links,
retaining native figure/caption and attribute handling. Other export backends,
including LaTeX/PDF, report an explicit error rather than omitting a diagram.
The existing PNG sharing command `my/excali-export` is unchanged.

- **HTML:** Each SVG is embedded in its image's `src` as a base64 data URL.
  No diagram asset folder is required. Separate image documents also prevent
  collisions between native SVG glyph/clip identifiers. This is a single-file
  diagram delivery experiment, **not a guarantee of one-step import**: services
  may strip data URLs or SVG, reject large files, or require separate uploads.
  Ordinary non-Excalidraw images and other external resources are not bundled.
- **Markdown backup:** Export copies the required SVGs into
  **`{basename}-assets/`**, alongside the output Markdown, and uses relative,
  URL-escaped image paths. For `design.md`, share `design.md` together with
  `design-assets/`. Buffer/string exports use the input Org basename and place
  assets beside that input. Export creates directories and reuses content-keyed
  filenames; it does not prune older assets. Assets are publication output,
  not authoritative scene files or committed preview assets.
  The destination must support SVG and accept accompanying files. Pasting or
  uploading Markdown alone may still need manual image uploads and URL changes.
  Markdown image sizing and caption/title presentation depend on the reader;
  a caption is not guaranteed to appear as a visible figure legend.

Both preview and publication generation require the configured Emacs 32+ native
excali renderer, its native module/fonts, usable scene palette metadata, and the
installed target palette. Inline previews additionally require SVG image display
support; publication needs the module's Cairo SVG export support. There is no
silent PNG fallback or additional conversion tool. Missing sources, invalid palettes, empty scenes and
renderer failures are reported; interactive preview failures leave the link
visible, while publication failures stop export. Publication uses the saved
source and never saves/restyles the authoritative scene.

Org comment-block bodies inherit the theme's `shadow` face with italic text;
their delimiters and comment/export semantics remain native. Org and Markdown
enable `visual-line-mode` automatically, without continuation indicators or
forced fringe widths. This wraps to window width without inserting newlines;
unrelated fringe indicators and widths are preserved.
Writeroom keeps its existing width, scaling and layout restoration, and now
restores the prior wrapping state on exit.

## Agent use and JSON

Keep `.excalidraw` JSON authoritative. Copy `canvas` to
`appState.viewBackgroundColor`. Map preset `stroke` to `strokeColor`, `fill` to
`backgroundColor`, and use `fillStyle: "solid"` for filled shapes. Set label
elements' `strokeColor` from the paired `text`, checking it against the fill
actually behind the label. Standalone text and arrow labels sit on the canvas.
Do not use a box's text/fill pair blindly for those labels. New-item defaults
can be stored as `appState.currentItemStrokeColor`,
`currentItemBackgroundColor` and `currentItemFillStyle` in native files.

### Constructing theme-portable diagrams

- Prefer native bound labels where appropriate. Set the text's `containerId`
  and the container's reciprocal `boundElements` entry so the editor knows the
  label's background. Merely positioning text over a box does not bind it;
  conversion treats unbound text as sitting on the canvas, not the box fill.
- When separate label backplates are needed, use rectangles with
  `strokeColor: "transparent"`, `fillStyle: "solid"`, and `backgroundColor`
  copied from the palette's `canvas`. These follow explicit palette conversion
  as described above. Do not invent a near-canvas shade. Unbound text over these
  backplates uses the canvas text-contrast rule.
- Use named colour presets for meaningful distinctions, not decoration, and
  keep their meaning consistent within a diagram. Read the selected theme's
  palette; do not substitute fixed hex values or hand-mixed shades. Use the
  stroke/fill/text triple together for filled boxes, with text contrast checked
  against the actual fill. Standalone and arrow labels require a canvas check,
  including when using named colours. Use the same 4.5:1 contrast threshold as
  the editor, falling back to black or white when the preferred ink fails.
- Never make colour the only distinction: retain descriptive labels or another
  visual cue, such as a meaningful line pattern.
- Before handing off a generated diagram, verify explicit conversion to at
  least one light and one dark palette on a disposable copy. Check labels,
  backplates and canvas together, not only box fills. Preserve the original
  diagram; disclose any ambiguous/unconverted styling.

For a new drawing, ask which theme to use if it was not supplied; do not assume
the user's current theme from a palette filename or yesterday's drawing.
The example image-rollout diagram originally used hand-picked fills, not this
generated palette. Its service boxes correspond to Neutral, Mitch's boxes to
Accented, messages/headings to Default, and lifelines/phase boundaries to Muted.
Generated Doric Earth colours intentionally differ from that demo.

Editor-created drawings store the current palette JSON object directly:

```json
"palette": {
  "version": 1,
  "theme": "doric-earth",
  "canvas": "…",
  "presets": "…"
}
```

Use the complete palette JSON object, not the illustrative ellipses above.
Agents creating new diagrams should write the same field and replace it whenever
they convert the diagram. Preserve unrelated fields, including element
`customData`. No per-element roles are recorded. The old `homeConfigPalette`
wrapper with `initialPalette`, `initialTheme` and `currentPalette` is not supported: migrate those files
directly, retaining the old current snapshot when present, otherwise the initial
snapshot. This migration changes metadata only, not painted colours.

The pinned excali-mode preserves this metadata and native current-item defaults
through save/reopen. **Browser Excalidraw exports discard the top-level metadata
and current-item defaults**, but preserve the painted colours and canvas.
Where the diagrams directory is version-controlled, missing palette metadata
may be recovered from Git history. Do not create commits automatically.

For an agent-side theme conversion, use `palette` as the source and a generated JSON file as the
target. Without roles, equal colours can be
ambiguous: consider element types, fill/stroke combinations and bound-label
relationships, preserve unmatched/explicit colours, and ask about ambiguities.
Review the diff before replacing a drawing and record the target snapshot in
`palette` after conversion. The editor
command above provides explicit conversion; opening and theme changes also
follow the current palette automatically when safe, as described above.
